# 后端开发守则（FastAPI 版）

讲清楚每个模块“是什么、为什么这么设计、怎么讲给评委听”，以及路演避坑要点。旧版 SpringBoot 源码保留在 `src/` 仅作参考，当前运行的是 `app/` 下的 FastAPI 工程。

---

## 一、整体架构与数据流向

系统分三层：

- **端（ESP32-S3 / ESP32-CAM）**：采集传感器、执行蜂鸣器/补光灯/舵机/音量屏幕控制，不跑 AI；
- **边（香橙派）**：摄像头拍照、YOLO 人形识别、视频流，承担 AI 算力；
- **云（本后端）**：MQTT 收发预留、图片存储、数据入库、对前端提供 REST 接口、设备状态管理、大模型密钥代理。

最小链路数据流：

```
ESP32 上报遥测/告警（MQTT 或 HTTP）
  → 后端落库（companion_device / pet / sensor_data / alarm_record…）
  → 前端经 REST 接口读取设备状态、档案、图表、告警
前端操作（音量/开关/云台/喂食）
  → 后端 REST 接口
  → MQTT 下行指令到设备（未接 Broker 时仅打印日志）
```

## 二、目录分层与每个模块的职责

| 模块 | 职责 | 关键文件 |
| --- | --- | --- |
| `app/main.py` | 应用入口：创建 FastAPI、CORS、静态目录、注册路由、启动建表 | `main.py` |
| `app/config.py` | 读取 `.env`/环境变量，全局配置单例，判断外部服务是否启用 | `config.py` |
| `app/database.py` | SQLite 连接、建表 DDL、种子初始化、设置项读写 | `database.py` |
| `app/seed.py` | 与前端原型演示数据一一对应的种子数据 | `seed.py` |
| `app/common/response.py` | 统一响应壳 `{code,message,data}`、业务异常、全局异常处理 | `response.py` |
| `app/services/llm.py` | 大模型代理：OpenAI 兼容调用，未配置/失败走兜底话术 | `llm.py` |
| `app/services/mqtt.py` | MQTT 预留客户端：连接、发布；未配置时空操作 + 日志 | `mqtt.py` |
| `app/routers/companion.py` | 陪伴域接口：设备/宠物/聊天/插件/记忆/设置/天气 | `companion.py` |
| `app/routers/monitor.py` | 监控域接口：传感器/告警/指令/大屏统计 | `monitor.py` |

分层原则：**router 只收请求返结果，service 写业务规则，database 只管读写库**；改数据库不影响接口，改业务不动页面。

## 三、八个核心“为什么”

### 1. 为什么选 FastAPI 而不是继续用 SpringBoot

- 竞赛机器上 Python 环境现成、启动快、依赖轻；FastAPI 自带 Swagger 文档，接口字段一眼可见；
- 前端是 Vue/JS 技术栈，后端用 Python 便于同学全栈理解；
- 旧 Java 工程保留作参考，需要 Java 部署时可在 `backend/` 目录手动执行 `mvn spring-boot:run`（需 JDK17）。

### 2. 为什么默认用 SQLite 而不是 MySQL

- 路演换电脑最怕环境问题：SQLite 是单文件内嵌库，免安装、免服务，删文件即重置；
- 表结构与 MySQL 脚本一致，正式部署时导入 `sql/petos_companion_mysql.sql` 即可平滑切换；
- 数据量小（演示级），SQLite 读写完全够用。

### 3. 为什么硬件通信用 MQTT 而不是 HTTP

- 硬件网络不稳定、设备可能休眠，MQTT 为弱网物联网设计，长连接、开销小、省电；
- 发布/订阅天然一对多，后端和香橙派可同时收同一告警；
- 有 QoS、遗嘱和心跳机制；HTTP 一问一答短连接，硬件轮询费电、实时性差。

### 4. 为什么 ESP32 不跑 YOLO，算力交给香橙派

- ESP32-S3 内存算力有限，跑不动神经网络；它只做低功耗实时采集与执行；
- 香橙派 CPU/内存与摄像头接口更强，适合跑视觉模型；专业硬件做专业的事，系统更稳、成本更低。

### 5. 为什么后端只做转发和存储，不参与 AI 识别

- 后端要同时服务前端和多台设备，参与重计算会拖慢接口；
- AI 识别离摄像头/模型越近链路越短；后端职责单一（消息、存储、接口），出问题好定位，也方便独立扩容或替换 AI 模块。

### 6. 为什么大模型密钥必须放后端

- 前端代码和浏览器请求都可被查看，密钥放前端等于公开；
- 前端只调自己后端 `/api/chat`，后端携带密钥请求第三方，密钥不出后端；模型不可用时后端兜底，演示不中断。

### 7. 为什么图片走 HTTP 上传而不走 MQTT

- 图片体积大，会撑爆 MQTT 消息负载、拖慢实时通信；
- MQTT 只传小体积事件与指令，图片走 multipart HTTP 存本地目录，经 `/images/` 静态访问。

### 8. 为什么统一响应壳 `{code, message, data}`

- 所有接口同一结构，前端一套解析代码通用；`code=0` 成功，非 0 失败，`message` 可直接展示；
- 全局异常处理器兜底，未预期错误也返回统一壳，不向前端抛堆栈。

## 四、编码纪律

1. 命名见名知意，不使用含糊缩写；
2. 核心逻辑必须写中文注释，说明“做什么、为什么”；
3. 不擅自引入复杂中间件，最小版本优先保证整条链路跑通；
4. 所有接口统一用响应壳封装，异常走全局处理器；
5. 外部服务（MQTT/大模型/摄像头）未配置时必须能降级运行，不能启动失败；
6. 接口字段名与前端模板读取的字段严格对齐（camelCase，如 `petKey`、`activeDeviceId`）。

## 五、风险点与排查

| 现象 | 可能原因 | 排查步骤 |
| --- | --- | --- |
| 后端起不来 | 8080 端口占用、依赖未装 | 看启动报错；`python -m pip install -r requirements.txt`；确认端口空闲 |
| 前端拿不到数据 | 代理目标错、后端未起、路径错 | 确认后端 8080；浏览器 Network 看 `/api` 状态码；核对 Vite 代理 |
| 聊天一直是兜底话术 | 大模型地址/密钥未配或调用失败 | 看后端日志 `[LLM]` 提示；核对 `.env` 的 `LLM_BASE_URL`/`LLM_API_KEY` |
| 指令下发无反应 | MQTT 未连接 | 日志 `[MQTT]` 是否演示模式；确认 Broker 启动、账号一致、已装 paho-mqtt |
| 图片不显示 | 静态目录/路径错 | 直接访问 `/images/文件名`；确认 `upload-images` 目录存在 |
| 数据想重置 | 演示数据被改动 | 停后端，删除 `petos.db`，重启自动重新灌种子 |
| MySQL 连接失败 | 地址/账号/驱动问题 | 核对连接串；安装 PyMySQL；确认已导入建库脚本 |

通用排查顺序：**后端控制台日志 → 数据库（petos.db / MySQL）→ Broker 控制台 → 前端 Network**，四段一查，问题基本能定位。
